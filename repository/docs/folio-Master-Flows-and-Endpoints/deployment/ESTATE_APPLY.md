# Estate apply — every flow update and reference-data change in one pass

`ESTATE_APPLY.console.js` applies everything this repository holds for the live estate, from your
own browser session:

- the 20 flow packages;
- the Departments and Categories list changes.

It needs no PowerShell, Entra ID, Azure or admin rights. It changes only the flows you own or
co-own, and only the lists you can edit.

The identification packages (Phases 3 and 4) are not here: [FLOWS_UPDATE.md](./FLOWS_UPDATE.md) applies all of them
with one command, `npm run flows:update`.

The file, and its command-line twin `estate-apply.cli.mjs`, are generated by `node scripts/build-estate-apply.mjs` and tested by
`tests/estate-apply.test.mjs` against a simulated tenant. Regenerate the file after any package
changes.

## Run it

| Where | Paste the file, then | What happens |
|---|---|---|
| **Power Automate** tab: `https://make.powerautomate.com`, **My flows** open. Don't reload the page after opening it | Paste the file (it plans automatically), then run `await ESTATE.apply()` | **Plan:** a table of each package, its target flow, a status and the reason. **Apply:** downloads a backup of every flow it will change, then writes, then reads each flow back |
| **SharePoint** tab: any page on `https://nitdanigeria.sharepoint.com` | Paste the same file, then run `await ESTATE.data.apply()` | Adds the approved units missing from the Departments list, applies the owner's category moves, then re-reads the lists to confirm the changes |

Other commands:

- `await ESTATE.apply({ only: ['Portal_VERIFY_ECM_DOCS'] })` applies a subset.
- `await ESTATE.repoint()` moves keys to their own flow; see below.
- `await ESTATE.rollback()` restores every flow changed from that browser tab.

Every apply downloads a run report as JSON; it contains no credentials.

**If it cannot read your session.** The tool first tries to reuse the portal's own sign-in. It
waits 20 seconds for that, then prints the steps below. It never prints a token.

Some portal builds keep that sign-in out of reach of a console paste. In that case, hand it over
by hand:

1. Open DevTools (F12) and select the **Network** tab. Type `ProcessSimple` in its filter box.
2. Click **My flows** in the portal's left menu.
3. Click a row whose **Type** is `fetch` or `xhr`, not `preflight`. Open **Headers**, then
   **Request Headers**, and find `authorization`.
4. Right-click the value and choose **Copy value**. It starts with `Bearer ey`.
5. In the Console, run `ESTATE.useToken('<paste>')`, then `await ESTATE.plan()`.

`useToken` checks the token against the Flow service before using it. It keeps the token in that
tab's memory only.

The token is your sign-in for about an hour. Do not send it to anyone or save it in a file. If a
later command fails with 401, copy a fresh token and run `useToken` again.

`await ESTATE.diagnose()` shows the hosts the tab called and the token audiences it saw.

## Command-line route (Termux, or any machine with Node.js 18+)

`estate-apply.cli.mjs` holds the same runtime, packages and checks as the console file. It signs in
the way the correspondence mailer's setup does: with a code on a Microsoft page. You copy no token,
and it needs no app registration or admin rights. It goes through Microsoft's own public sign-in app ("Microsoft
Azure PowerShell"), then the Power Platform CLI app if the first is refused. A dropped connection
is retried.

1. Copy `docs/folio-Master-Flows-and-Endpoints/deployment/estate-apply.cli.mjs` to the phone, for example into `~/storage/downloads`.
2. In Termux:
   ```
   termux-wake-lock
   cd ~/storage/downloads
   node estate-apply.cli.mjs plan
   ```
3. It prints a web address and a code. Open the address on any device, enter the code, and sign
   in with the account that owns the flows. The command then carries on by itself.
4. Read the plan. To write, run `node estate-apply.cli.mjs apply`. It signs in again with a new code.

| Command | What it does |
|---|---|
| `plan [--only A,B]` | Reads only; the same table as the console. With `--only` naming packages that have endpoint keys, it reads only the flows attributed to keys |
| `apply` | Backs up, writes, reads each flow back; `--only A,B` and `--repointed K,…` as in the console |
| `repoint` | Writes the `DGO_ENDPOINT_<KEY>=<url>` lines to a file readable only by you; delete it after use |
| `run <flow-id> [<run-id>] [--last N]` | Reads only. Lists a flow's recent runs; for the run named (or else the newest failed one) it lists each action that failed on its own account, with the service's error code and message. A connector action's reason comes from its outputs, which sit behind a signed link: the link is read and never shown |
| `restore <estate-backup-….json>` | Puts back every flow in a backup and confirms each by reading it back |
| `values [--repointed K,…]` | Reads every wired flow's trigger address and writes `dgo-values.txt` (readable only by you): one `PF_ENDPOINT_<KEY>=` line per portal key and one `DGO_ENDPOINT_<KEY>=` line per internal-platform key, the format `npm run package -- --values` reads. Keys it cannot resolve are listed as MISSING. Prints no address. Delete the file after the build |

Backups, run reports and repoint values go to `../../deployment/estate-apply-output`, or `--out <dir>`.

**Which flows are read.** A key is wired to a workflow ID, the 32-character ID inside its trigger
address, and the only way to learn which flow answers an ID is to read that flow's trigger. A full
`plan` therefore reads every flow the account can see, since three packages (USERDIRECTORY_SYNC,
SCHEDULED_SWEEP, FLOW_TRUTH_PERSISTENCE) are found by what a flow contains. Work that concerns
keys alone (`values`, `repoint`, and `plan` or `apply` with `--only` naming key packages) reads
only the flows the repository attributes to keys: the owner's map, the 2026-09-18 reading, the
newest `*-live-endpoint-wiring.json` evidence and the migration targets. If any wired workflow ID
is not answered by one of them, it says so and reads the rest. In a narrow run, a package found
by its contents shows `NOT_READ`.

The SharePoint reference data still runs from a SharePoint tab (`ESTATE.data.apply()`). The
command-line sign-in covers the Flow service only.

## Statuses

| Status | Meaning | Your action |
|---|---|---|
| `WILL_UPDATE` | Target found, package installs cleanly, content differs | Run `ESTATE.apply()` |
| `UP_TO_DATE` | The flow already carries the package | None |
| `STAGED` | Installed in the key's own flow, which nothing calls yet | Run `ESTATE.repoint()` |
| `APPLIED` | Written and read back: every action, every variable value and the trigger are confirmed | Exercise the endpoint |
| `HELD` | A prerequisite is not current (runbook §0.4) | Clear the prerequisite first |
| `BLOCKED` | Refused for the reason shown | Follow the reason |
| `FAILED` | The service refused the write, or the read-back didn't match (that flow was then restored) | The run stops; read the reason |
| `NOT_RUN` | The run stopped at an earlier failure | Re-run once the failure is fixed |

## How targets are found

The target for an HTTP package is found **live**, not from a typed list of flow IDs:

1. For each package's contract key, `config/endpoint-atlas.data.js` (built from the endpoint
   register) gives the workflow ID the platform calls.
2. For each flow you own, the tool reads its trigger's callback URL and keeps only the workflow ID
   in it.
3. The package goes to the one flow whose workflow ID matches.

The callback URL is a credential. The tool never stores or prints it.

Flows without an endpoint key are found by their own actions:
- the directory sync: `Scope_Global` holding `Search_for_users_V2`;
- the scheduled sweep: `Scope_Scheduled_Sweep`;
- flow-truth persistence: its scope, inside its host flow.

## Keys that move to their own flow

The endpoint register wires three pairs of keys to one flow each (four keys move). The packages and contracts give
each key its own flow:

| Key | Shares today with | Moves to | Source |
|---|---|---|---|
| `OTP_VERIFY` (or `OTP_GENERATE`, whichever is not on the wired flow) | the other OTP key | `IP_OTP_VERIFY` `4dbe6dde…` / `IP_OTP_Endpoint` `913bd078…` | `contract-key-flow-map.json`, decided 2026-09-24 |
| `DYNAMIC_ACTIONS` | `SUBSIDIARY_ACTIONS` | `IP_Dynamic_Global_Actions_Endpoint` `31c0aaf0…` | `contract-key-flow-map.json` |
| `SUBSIDIARY_ACTIONS` | `DYNAMIC_ACTIONS` | `IP_Subsidiary_Actions_Endpoint` `08da1783…`, which must implement all 18 routes in `config/endpoints.config.js` (`routeKeys`) | `contract-key-flow-map.json` |
| `FETCH_ACTIVITIES` | `GET_DOCS` | the `SUBSIDIARY_ACTIONS` flow (its new one when it moves), which must implement `LIST-ACTIVITIES` | `config/endpoints.config.js` (`sourceKey`, `action`) |

The run of 2026-09-27 read `DYNAMIC_ACTIONS` as `DONE`: `IP_Dynamic_Global_Actions_Endpoint`
already answers the workflow ID both `DYNAMIC_ACTIONS` and `SUBSIDIARY_ACTIONS` are wired to. So the
key that moves out of that pair is `SUBSIDIARY_ACTIONS`, and `FETCH_ACTIVITIES` follows it. Neither
can move yet: the same run found `IP_Subsidiary_Actions_Endpoint` without `LIST-ACTIVITIES`, and the
export held of it (`docs/folio-Master-Flows-and-Endpoints/exports`, 2026-09-05) implements none of the 18 routes. The
plan shows the move `BLOCKED` with the missing routes, and `values --repointed` refuses it. Evidence:
`docs/folio-Master-Flows-and-Endpoints/deployment/internal/evidence/2026-09-27-live-endpoint-wiring.json`.

The service adds `inputs.authentication` to every connector action it stores, so a flow never
matches its package byte for byte after a write. The plan ignores that one field and nothing else:
a flow that differs only by it reads `UP_TO_DATE` (or `STAGED` for a moving key's own flow), and
any other difference, including one inside an action's parameters such as a `$filter`, reads
`WILL_UPDATE` and names the first differing field.

`AI_CHAT`, `AI_DOC_ANALYSIS` and `AI_EMAIL_ANALYSIS` also share one flow (`AI_Document_Processing`).
That is by design: `contract-key-flow-map.json` marks them `SHARED_CONTRACT_KEYS`, and
`npm run package` allows it.

The packager already treats today's wiring as a defect. All three pairs are keys with different
`sourceKey`s on one workflow, which `npm run package` refuses to build ("workflow-collision").
After the move:
- each OTP key has its own flow;
- `DYNAMIC_ACTIONS` and `SUBSIDIARY_ACTIONS` each have their own flow;
- `FETCH_ACTIVITIES` shares only with `SUBSIDIARY_ACTIONS`, its declared source, which the
  packager allows.

The plan shows these in a second table. The move takes three steps, and no endpoint goes down at
any point:

| Step | Command | What happens |
|---|---|---|
| 1 | `await ESTATE.apply()` | **Stages** each moving key's package into its own flow while nothing calls that flow (status `STAGED`). Flows the platform still calls for another key are not touched |
| 2 | `await ESTATE.repoint()` | Copies `DGO_ENDPOINT_<KEY>=<url>` lines to the clipboard, never to the console. Replace those keys in your values file, run `npm run package -- --values <file>`, redeploy, and sign in once |
| 3 | `await ESTATE.apply({ repointed: ['OTP_GENERATE', 'SUBSIDIARY_ACTIONS', 'FETCH_ACTIVITIES'] })` | Installs the packages into the flows those keys used to share (`OTP_VERIFY`, `DYNAMIC_ACTIONS`, `GET_DOCS`), then releases every internal package that was waiting for the OTP pair |

On the command line, `values --repointed K,…` writes a whole values file with the moved keys
already on their new flows, in place of step 2's copy-and-replace.

Pass only the keys you actually repointed. The run report records the new wiring (key, flow and
workflow ID; no URLs). Send it back so the endpoint register can be updated to match.

## What it refuses

- **A flow that still serves a key the package doesn't implement.** Replacing its body would take
  the other endpoint down. For the three pairs above, the reason shows the `repointed` call that
  frees the flow.
- **A move to a flow that doesn't implement the key**, for example a subsidiary flow without
  `LIST-ACTIVITIES`. Also a staging target the platform already calls for another key.
- **Two packages on one flow**, **no matching flow**, or **more than one** matching flow.
- **A package that doesn't install cleanly.** Examples: a `runAfter` that names no sibling, a
  connector host in clipboard spelling, a variable write with no value, or an action that reads a
  branch that isn't certain to have finished.
- **A live dependant whose prerequisite isn't live.**
  - SUBMISSION, STATUS and WRITEBACK wait for VERIFY and VERIFY_CONFIRM.
  - UPLOAD waits for SUBMISSION.
  - Every other internal flow waits for the OTP pair.

  A staged package counts as not yet live. Staging itself has no prerequisites, because it touches
  nothing the platform calls.

It never deletes or creates a flow, list item or column. For reference data it only adds missing
units and updates the owner's decided category rows. It never changes an existing department row.

## What a write does

It uses the same installer as `patch-flow-package.mjs --install` (`scripts/lib/flow-install.mjs`),
so both routes produce identical definitions. For each flow it:

- places the Initialize variable actions at the top level, then the package's scope after them;
- converts connector hosts to the spelling a saved definition uses;
- keeps existing connection references and adds any the package needs;
- sets the trigger to the HTTP method in the endpoint contract (PUT for UPLOAD and SCAN_INTAKE);
- for the directory sync, sets the trigger to daily at 05:45 WAT.

The trigger keeps its identity, so trigger URLs do not change.

## Supersedes

This tool supersedes the per-flow `folio-Master-Flows-and-Endpoints/surfaces/internal/console-apply/*.console-apply.js` snippets.
Those snippets have two addressing faults:

- **Flow ID:** they address each flow by the 32-hex workflow ID, but the Flow API addresses a flow
  by its flow name (a GUID). For example, IP_Reference_Data_Endpoint's flow name is `9a4dea8e-…`
  and its workflow ID is `885fad5e…`.
- **Environment:** they use `defaultca6a4b3f…`, but the tenant inventory records the environment
  as `Default-ca6a4b3f-9123-49bc-bcb9-27085ebbf1a1`.
