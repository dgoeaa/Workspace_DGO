# What the portal client does with what the flows return

`docs/folio-Master-Flows-and-Endpoints/contracts/DOCUMENT_PORTAL_FLOWS.html` records a live-tenant probe of all six
portal endpoints, captured 2026-08-08, traced to the exact call site in `document-portal/js/`.
Its findings are about the **client**: what a citizen sees when a flow answers the way it
actually answers.

This page pairs each of those findings with the flow-side work, and says plainly which are
answered by a remediation visit and which are not. It exists because the two halves were
recorded separately — the flow defects in `DECISIONS.md`, the client consequences in the HTML
reference — and a defect is only closed when both halves are.

**Nothing here is new analysis.** Every finding is quoted from that reference; the column that
is mine is the last one.

---

## The findings

### 1 · A submission reports delivered while its attachments are never sent

> `uploadAll()` runs zero iterations when `res.uploads` is empty (the live-observed case) —
> attachments are silently never transmitted while the submission still reports `delivered`.

**Root cause, from the same document:** the harvested SUBMISSION trigger expects one inline
base64 file — `UserId` / `SubmitterName` / `EmailAddress` / `FileName` / `FileContentBase64`.
The client sends `localId` / `sender.name` / `senderEmail` and an `attachments[]` array **with no
bytes at all**. Neither the field names nor the cardinality match.

**Severity:** a citizen is told their document was received. It was not.

**Answered?** **Partly.** Visit 2 creates `Portal Upload Tickets` and visit 5 redeems them, which
is the mechanism that would populate `res.uploads`. **The schema mismatch itself is not in any
artifact** — no remediation changes the SUBMISSION trigger schema or the client's request shape.

---

### 2 · `verification_required` is indistinguishable from any other failure

> `verification_required` is classified identically to every other queued failure — `submit.js`
> has no branch that re-runs VERIFY / VERIFY_CONFIRM the way `track.js` does for STATUS.

**Severity:** a submission that only needed an email check is queued as if the registry had
refused it, and never retried.

**Answered? Yes**, client-side. `dispatchToWorkflow()` in `submit.js` now branches on
`reason === 'verification-required'` and runs the same client-half round-trip `track.js` already
carries — `requireVerification()` sends the code, collects it inline on the receipt page, and
retries `PF.intake.submit()` once with the proof. The outbox is untouched: a queued retry still
cannot run an interactive code exchange, so this only fires on the live submission, not on
background flush. Verified against `tests/hardening.test.mjs`; no artifact changes.

---

### 3 · `stored: false` is recorded as a successful upload

> `uploadAll()` in `submit.js` reads only `r.ok` and never separately checks `stored` — a
> `200 {"stored": false}` response is currently recorded as a successful upload, even though
> `PF.storage.upload()` itself distinguishes the two.

**Answered? Yes**, client-side. `uploadAll()` in `submit.js` now checks `r.stored` alongside
`r.ok`; a `200 {"stored": false}` response is pushed to `failed` and reported to the submitter
exactly as a transport failure already was, instead of counting as delivered.

---

### 4 · The support case reference the citizen is shown is invented locally

> `support.js`'s `send()` calls `PF.storage.support({...})` with no `.then()`, no assignment. The
> reference shown to the citizen (`ticket.ref`, generated by the local `sref()` function) exists
> before this call is even made and is never reconciled with `data.caseRef`. Whatever the flow
> returns, on any request, has zero effect on what the citizen sees.

**Severity:** the citizen quotes a reference that exists in no system of record.

**Answered? Yes**, client-side. Visit 5's `Portal Support Cases` row gives the reference
something to reconcile *against*; `send()` now awaits `PF.intake.support()` and, when it
delivers a `caseRef` that differs from the locally minted one, rewrites the stored ticket and the
receipt to it before either is shown. Filed offline or before a flow is configured, the local
reference is still shown immediately — it is provisional, not fabricated, and nothing in this
path claims otherwise.

---

### 5 · VERIFY answers 200 and the citizen is told it failed

> On the live-observed response (`ok: true`, `sent` absent → normalised `false` by strict
> `=== true` comparison), this takes the failure path — the citizen sees **"Could not send the
> code"** despite an HTTP 200.

**Answered?** **No.** Visit 1 rebuilds VERIFY's estate, rate limit and telemetry, and D8 makes an
explicit failure status survive the finalize scope. **Nothing in visit 1 makes the response body
carry `sent: true`.** The flow will keep answering 200 without it.

---

### 6 · VERIFY_CONFIRM answers 200 and a correct code reads as wrong

> On the live-observed response (`verification` absent), `track.js`'s `!r.ok || !r.verification`
> branch takes the failure path — the citizen sees **"That code was not accepted,"**
> indistinguishable from a genuinely wrong code.

**Answered?** **Yes.** Visit 1 adds `Create_Verification_Proof`, which mints the opaque token the
response is missing. This is the same gap D9 records from the flow side: the proof was never
minted, so C1 never completed.

---

### 7 · An unknown reference is answered 200 and rendered as "found"

> The probe's reference was unknown by construction and the documented contract requires **404**
> here. The live flow answered **200**. Because `res.record` resolves to `null` and the client's
> success branch is keyed on `r.ok` alone, `resolution` becomes `found` — not `denied`.
> `track.js` renders a near-empty but "successfully found" record via `fromRegistry(null, id)`,
> **indistinguishable in the UI from a genuine minimal-data match.**

**Severity:** the denial path fails open. Any reference at all is reported as found. The
documented contract's uniform 404/400 denial — which exists precisely so a stranger cannot
distinguish "no such reference" from "not yours" — never fires.

**Answered?** **No.** Visit 3 gives STATUS a `$filter` so it can look a reference up. **Nothing
says what it must return when the lookup finds nothing.** Without that, adding the filter makes
the flow query correctly and still answer 200 with an empty record.

## Summary

| # | Finding | Fixed by | Status |
|---|---|---|---|
| 1 | Attachments never transmitted | visit 2 + visit 5 mechanism; schema mismatch unowned | **partly** |
| 2 | `verification_required` not retried | client — `submit.js` | **yes** |
| 3 | `stored: false` counted as success | client — `submit.js` | **yes** |
| 4 | Support reference never reconciled | client — `support.js` | **yes** |
| 5 | VERIFY 200 without `sent` | — | **no** |
| 6 | VERIFY_CONFIRM 200 without `verification` | visit 1, `Create_Verification_Proof` | **yes** |
| 7 | Unknown reference answered 200 as "found" | — | **no** |

**Four of seven are answered.** Three of the remaining four are flow-side — a body field
(`sent`), a lookup's not-found response, and a trigger schema shared with visit 2's mechanism —
and none has an artifact yet. The fourth client-side item this page used to list, item 1's
schema mismatch, stays partly open for the same reason: the mechanism exists once visits 2 and 5
land, but nothing has specified the request shape both sides agree on.

That is the gap this page exists to make visible: the remediation was scoped to move flows onto
the provisioned estate and bring them onto the build standard. It was never scoped to make the
citizen-visible behaviour correct, and those are not the same thing.

---

## What this changes about "done"

A visit that moves its flow's writes onto the portal estate and scores 100% on the build standard
can still leave a citizen told their document arrived when it did not (1), or told a correct code
was refused (5) — neither is a client defect, and neither is answered by any visit.

**So `npm run wiring` reading 59/59 is not the finish line.** It is the point at which the
estate is correct. The finish line is the end-to-end pass in `HANDOVER.md` step 7 — submit,
verify, track, upload, support — checked against the citizen-visible outcomes in the reference
document, not against the wiring count.
